# DiningPage (`/dining`)

## Purpose

Shows UGA's 6 dining halls as a card list, each card showing a preview of today's menu for the current meal (breakfast / lunch / dinner). Favorited dining halls are sorted to the top of the list.

## Data sources

- **Menu**: rather than calling [Nutrislice](https://uga.nutrislice.com) (`uga.api.nutrislice.com`) directly — CORS is blocked — the Amplify custom query `getDiningMenu` (`amplify/data/resource.ts`, handler at `amplify/data/get-dining-menu/handler.ts`) calls it server-side and proxies the result. `DiningHallCard` calls `client.queries.getDiningMenu({ hallSlug, mealType })` per dining hall (`hall`) and meal (`mealType`) — with 6 cards that is 6 independent queries (no batching/caching).
- **Hours**: there is no realtime API, so per-weekday hours are hardcoded in `src/lib/diningHours.ts` (transcribed by hand from the dining.uga.edu pages). If UGA changes hours mid-semester, a manual update is needed.
- **The 6 dining halls** (`DINING_HALLS` in `src/lib/dining.ts`, also the default card display order): `bolton`, `hillside`, `oglethorpe`, `snelling`, `niche`, `villageSummit`. Names are shown via `dining.halls.*` (i18n).

## Things to know

- **Meal type (`mealType`) is decided once, on entry**: `DiningPage` computes it once at mount via `useState(() => getCurrentMealType())` (breakfast before 10:00, lunch before 15:00, dinner otherwise). If you leave the page open across a meal boundary it is not recomputed — you have to refresh.
- **The meal's hours are shown in grey next to the meal label on the card**: `S.MenuRow` in `DiningHallCard` (the red `t('dining.mealTypes.…')` label + the grey `getDiningMealHoursToday(hall, mealType)` time). It uses the same data source as the detail page's meal tabs (`DINING_MEAL_HOURS` in `src/lib/diningHours.ts`), and a parenthetical caveat (e.g. Niche's "HSC residents only") is trimmed off with `splitHoursNote`, showing only the time — this one-line label has no room to show it on a separate line like the detail page does.
- **Favorites**: stored in localStorage via `useFavorites('dawghub:dining:favorites')` (not an Amplify model, unrelated to sign-in). `sortHallsByFavorite` is not a stable sort that only pulls favorites forward while keeping the rest in original order (it is a plain boolean-comparison sort).
- **The card's section order + pin indicator follow the pinned state**: a section pinned on the detail page (`DiningHallDetailPage`) — e.g. "Entrees" — shares `dawghub:dining:pinnedSections`, so it always floats to the top in this card preview too (`sortSectionsByPinned`, see [[DiningHallDetailPage]]), and a small pin icon (`S.PinIndicator`) appears next to the section title. The card's icon is not a button you can toggle, though — it is a read-only status indicator (pinning/unpinning is only possible on the detail page).
- **Menu deduplication is not real grouping**: `station_id`/`is_section_title` are always empty in the Nutrislice response, so real station separation is impossible — the Lambda only removes duplicates by name (`seenNames`) and imitates priority by pushing condiment/beverage/dessert keywords (`SECONDARY_SECTION_KEYWORDS`) to the back. `groupMenuItemsBySection` (`src/lib/dining.ts`) just takes the order the backend already sorted and puts it into a Map grouped by section.
- **Menu preview in a card shows at most 4 items per section** (`MAX_PREVIEW_ITEMS`); overflow is shown as "+N more". The full menu is on the detail page (`/dining/:hall`, `DiningHallDetailPage`).
- **Dietary/allergen tags** (`DietaryTags.tsx`) render only tags that have a mapping in `DIETARY_ICON_URLS` / `ALLERGEN_ICON_URLS` — icon slugs from Nutrislice with no mapping (e.g. `taste-of-home`) are already filtered out at the Lambda layer.
- **Filter the menu itself by dietary/allergen tags**: the gear button next to `PageTitle` (`S.TitleRow`) opens `TagSettingsModal` — it shows the 5 dietary and 9 allergen types as icon + name in two sections, each with a 2-way **Show / Hide** segment (`S.Segment`, both shown pill-shaped in one row, directly clickable). Tags set to "Hide" combine as OR (an item with any of them is dropped) — multiple tags can be hidden at once. **The "only" option (an AND filter keeping just items that have the tag) was deliberately dropped**: Nutrislice tagging is often applied only in ambiguous cases ("this dish is halal") and not at all to obviously safe items like orange juice, so filtering with "halal = only" would also remove untagged items that are actually fine and give a false sense that "everything in this list is safe" (a limitation of the tagging data that can't be fixed on the frontend — a 3-state version survives in earlier commit history). State is stored in `dawghub:dining:tagFilters` (`localStorage`, `useTagFilters()` in `src/pages/dining/tagFilters.ts`; `show` is the default so only `hide` overrides are stored), and the filter function `filterItemsByTagState` (`src/lib/dining.ts`) filters the menu-item array before section grouping, so it applies identically to both this list card and the detail page (`DiningHallDetailPage`) — the settings button is only on this page but the effect is global. When everything is filtered out, `dining.noMatch` is shown, distinct from "no menu". The modal header's "Reset" button (shown only when there are active filters) clears it all at once.
- **`useTagFilters` is backed by a module-level external store (`useSyncExternalStore`)**: it was first implemented with an independent `useState` per component, but `TagSettingsModal` (opened from the settings button) and several `DiningHallCard`s (6 in the list) are all mounted in `DiningPage` at once — so changing a filter in the modal didn't update the cards, which held the value they read once at mount (the pin feature had the same issue at first, but it just wasn't noticed because those pages aren't shown together). Now a `cachedFilters` module variable + a `listeners` Set means every `useTagFilters()` call site subscribes to one source, so they all re-render the moment it changes, wherever the change came from.
- **The brief skeleton on a filter change is not real loading — it's a deliberate effect**: filtering/grouping is all synchronous computation (`useMemo`), so the list would normally change the instant a button is pressed, which felt unnatural. `useTransitionFlash(tagFilters, 300)` (`src/lib/useTransitionFlash.ts`, a general-purpose hook) fakes a 300ms "loading" whenever the filter value changes — the button state itself changes immediately, and only the menu list briefly shows the existing network-loading skeleton (`isLoading || isFilterTransitioning`) again before settling on the new result. A `useRef` skips the first render so it does not flash once on mount. `DiningHallDetailPage` uses the same pattern.
- The map coordinates for Hillside/Niche/Village Summit are not in the official GIS and use manually researched values, but that is a map-display issue covered in `ai/pages/Map/MapPage.md` — unrelated to this list page itself.
- **Show the "next opening time" when currently closed**: decided by `isDiningHallOpenNow(hall)` / `getNextDiningOpen(hall)` (`src/lib/diningHours.ts`), shown in the card header (`S.NextOpen`) and the detail page header. **Both the all-day hours table (`DINING_HOURS`) and the per-meal hours table (`DINING_MEAL_HOURS`) must be checked together** for accuracy — using only one leaves gaps: with only the per-meal data, Hillside's "late night" (10pm–2am) matches none of breakfast/lunch/dinner and it is wrongly judged closed while actually open; with only the all-day table, Niche shows "7:00am–2:30pm" (dinner is only a parenthetical note) so its real 5–7pm dinner is missed (and The Niche genuinely has a closed gap from 2:30–5pm between lunch and dinner — the all-day table alone misses that gap too and can make it look open all day). So `allRangesForDay` combines the 3 per-meal ranges + 1 all-day range, 4 total, and checks whether "now" falls in one. Ranges crossing midnight (e.g. "7:00am–2:00am") add 24h to the end time, and yesterday's range carrying past midnight into today's early morning is checked separately. `getNextDiningOpen` scans up to 7 days ahead for the nearest future start time — shown as "today 5:00pm" / "tomorrow 7:00am" / "{{day}} 7:00am" (day label reuses the schedule page's `schedule.days.*` i18n).
