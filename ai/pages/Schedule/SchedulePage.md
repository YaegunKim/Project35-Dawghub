# SchedulePage

`src/pages/schedule/SchedulePage.tsx` (+ `SchedulePage.style.ts`); the pure grid-layout math lives in `src/lib/scheduleGrid.ts` (shared with the friend-schedule view).

## Purpose

Shows a weekly schedule as a day×time grid (5am–midnight, auto-expanding further if a class falls outside that range), and lets the user add/remove courses in two ways: "search and add" (based on UGA's official schedule-of-classes data) or "add manually" (manual entry). When adding via search, the instructor's RateMyProfessors rating/reviews are shown as well. Next to the page title is the Friends entry point, leading to friend requests/acceptance and viewing a friend's schedule.

## Data sources

- **`ClassEntry` (Amplify model, `amplify/data/resource.ts`)** — the actual stored schedule item. `courseCode` (required), `title`, `day` (required, `SUN`–`SAT` string), `startTime`/`endTime` (required, `"HH:MM"` 24-hour string), `location` (optional, free text), `locationLat`/`locationLng` (optional floats — only set when a location was picked on the map, see "Setting a class location" below). Authorization is `allow.owner()` only — you can only CRUD your own, there is no public read like the community boards. If a course meets on multiple days, one `ClassEntry` row is created per day (managed together by `courseCode` — deletion is also by `courseCode`, removing all day-rows for that course at once, `handleDelete`).
- **`searchUgaClasses` query** (Lambda, `amplify/data/search-uga-classes/handler.ts`) — called by the "Add a class" (search) flow. The "Schedule of Classes" page on `reg.uga.edu` fetches a CSV itself (`apps.reg.uga.edu/soc/{fall,spring,summer}.csv`); the server (Lambda) fetches and parses that CSV instead — the browser cannot fetch it directly because that endpoint has no CORS headers. If `term` is not passed, fall/summer/spring is auto-determined from the current month. Accepts optional `subject`/`level` arguments (e.g. `"4"` → 4000-level) for filtering — calling with neither returns a "browse all" listing. The CSV is cached at the module level for the Lambda instance's lifetime, so it isn't re-fetched/re-parsed on every search. It matches by course code / title and returns a meeting list including CRN, instructor, day, time, building, and room — i.e. the search flow auto-fills the room/time.
- **`getProfessorRating` / `getProfessorReviews` queries** (Lambda) — call RateMyProfessors' unofficial internal GraphQL API (`ratemyprofessors.com/graphql`) from the server (not an officially documented API, and RMP also has no CORS, so going through the server is required). Scoped by the UGA school ID (`schoolID`) to match only instructors whose name matches exactly; for same-name instructors it disambiguates with a `department` hint. Ratings are fetched in parallel automatically for every instructor in the search results (`fetchProfessorRatings`), and tapping a rating badge then lazily loads the review detail via `getProfessorReviews`. RMP reports `avgRating: 0` (not null) for instructors with zero reviews, so a rating is only shown when `numRatings > 0` (`hasRating()` guard) — otherwise it would misleadingly read "0.0".
- **`src/lib/ugaSubjects.ts`** — a static list of 229 UGA subject codes used by the Subject filter dropdown. Not fetched from the backend on every load — subject codes rarely change term to term, so a committed constant was judged sufficient. Refresh by re-extracting from UGA's SOC page and updating this file directly.
- **`fetchUgaBuildings`** (`src/lib/ugaBuildings.ts`) — the list of real UGA building names used for the datalist autocomplete on the "add manually" form's location `<input list>`. Same source as the Map page.
- **`Friendship` model / `findUserByEmail` / `getFriendSchedule` queries** — data sources for the Friends feature, see "Friends" below.

## Friends

- **Entry point**: an inline Friends button next to the page title ("Schedule") — `src/app/AppShell/FriendsDrawer.tsx`. Not fixed-position; it's a plain button on the same line as the title that scrolls with the page. It originally was a global floating button visible on every tab, but was moved to render only on Schedule/FriendSchedulePage after feedback that Friends should only appear within the Schedule tab — `AppShell.tsx` has no knowledge of this component at all now.
- **Data model**: `Friendship` (`amplify/data/resource.ts`) — `senderId`/`recipientId` (both `ownerDefinedIn`, two independent owner rules coexisting on one model) + `senderEmail`/`recipientEmail` (denormalized, so the request list can show emails directly) + `status` (`PENDING`/`ACCEPTED`/`DECLINED`/`BLOCKED`). `senderId`/`recipientId` are plain string fields, not the implicit auto-populated `owner` field, so the frontend must fill them in itself using the exact identity string format AppSync's owner authorization checks against: `${sub}::${username}`, assembled from `getCurrentUser()`'s `userId`/`username`.
- **Adding a friend**: the `findUserByEmail` Lambda query (Cognito `ListUsersCommand` lookup by email, `@uga.edu` only) checks whether the email belongs to an existing user; if found, the client calls `Friendship.create()` directly (only the privileged lookup needs a Lambda — creating the row itself is fine under normal owner authorization). Inviting a non-user (email invite) or a signup nudge isn't implemented yet — only works between two existing users (Phase 1 scope).
- **Viewing a friend's schedule**: the `getFriendSchedule` Lambda query (`amplify/data/get-friend-schedule/`) — `ClassEntry` is `allow.owner()` only, so a friend's schedule can't be read through the normal AppSync path. Instead, this one Lambda's execution role is granted direct DynamoDB read access to the `ClassEntry`/`Friendship` tables (`amplify/backend.ts`), and the handler itself verifies an `ACCEPTED` friendship with the caller (via `event.identity.sub`) before returning anything. Every other path still enforces `ClassEntry`'s owner-only restriction unchanged. `/friends/:friendUserId` (`FriendSchedulePage.tsx`) renders a read-only grid from this query, reusing the same `scheduleGrid.ts` layout functions as this page.

## Setting a class location on the map

- Next to the location field on the "add manually" form, a **"Set location" button** navigates to the Map page, where tapping the map drops a pin (an arbitrary point, not a building picker — the same UX as Directions' "pick on map").
- **Round-trip mechanism**: since the modal unmounts on navigation (losing its field state), the round trip goes through router state via `MapPickIntent`/`MapPickResultState` in `src/lib/mapNavigation.ts` — Schedule bundles every currently-typed field (`ScheduleDraft`, `src/lib/scheduleLocationPick.ts`) into `draft` and navigates to `/map`; Map enters pick mode and, on tap or cancel, navigates back to `/schedule` with `draft` carried through unchanged (plus `pickedLocation` — lat/lng/label — if the user tapped rather than cancelled). These types are siblings of the Dining tab's "See Location"/"Get Directions" `MapNavigationIntent` in the same file, and Map's code never needs to know what's inside `draft` (so other pages can reuse this same round trip).
- The picked coordinates are stored in `ClassEntry.locationLat`/`locationLng`, and the `location` text field is filled with the picked point's label. **Manually editing the location text afterward clears the coordinates** — they can no longer be assumed to match.

## Things to know

- **The README "Schedule ↔ Map integration" section is partly outdated**: it says "per-class room/time cannot be auto-looked-up, UGA Athena needs SSO", but `searchUgaClasses` (scraping the reg.uga.edu SOC CSV) was added later, so **in the search flow** building/room/time are auto-filled. That said, this is still an unofficial source (a CSV the registration page exposes for its widget), not an official API — it can break silently if the CSV structure changes (column names, etc.). The "add manually" flow is still 100% manual entry, so that constraint still applies there (though location specifically can now be pinned precisely via "Setting a class location" above).
- **Location text ↔ map integration**: if you put a UGA building name in `ClassEntry.location` (whether entered manually or auto-filled from search), the Map page matches that name to the real building coordinate and shows a 🎓 marker / highlight. The search result's `building`/`room` are joined into `location` as `[meeting.building, meeting.room].filter(Boolean).join(' ')`, so the search flow now satisfies the "string that starts with a building name" shape the Map-side matching logic expects (with the difference that the room text is appended after, unlike manual entry that puts only the building name). A pin dropped via "Set location" isn't a building name, so it doesn't participate in this marker matching — there's no separate map display using `locationLat`/`locationLng` yet (room for a future enhancement).
- **Search result UI**: shows the top 20 results first, loading more on scroll (infinite scroll). The Subject/Level filters are a custom Portal-based dropdown (to avoid the modal's `overflow:hidden` clipping a native `<select>`), defaulting to "browse all" when no filter is set. A result card's full course description only shows in a modal, opened via the "i" icon next to the course code (keeping the card itself compact). Sorted by course code first, then by instructor rating.
- **The RMP auth header is a hardcoded fixed value** (`Basic dGVzdDp0ZXN0`) — a public client credential used by RMP's own web app, not a secret, and already a well-known value. There is no separate account/key rotation doc.
- **Same-name instructor matching**: on the RMP side, if there are multiple candidates with an exact name match, it only tries to disambiguate by `department` substring containment — if that fails it just uses the first candidate. There is no guarantee of a perfect match.
- **Course color is hash-based** (`colorForCourse`, `src/lib/scheduleGrid.ts`): the `courseCode` string is hashed base-31 to pick an index into the `category.courses` palette — colors are not stored in the DB, so the same course always gets the same color, but if the palette size changes all existing courses' colors can be reshuffled.
- **Grid layout**: within a day, overlapping classes are split into columns and placed side by side by `layoutDay` (`src/lib/scheduleGrid.ts`, generic — also shared with the friend-schedule view's `FriendClassEntry`) (Google Calendar style). The grid's vertical range (`rangeStartHour`/`rangeEndHour`) defaults to 5am–midnight but auto-expands if there is an earlier or later class. On tablet/desktop, the search results' section list also switches to a CSS Grid (`repeat(auto-fill, minmax(180px, 1fr))`) so the narrow-screen vertical stack doesn't look stretched out on wide screens.
- **Section grouping** (`groupSections` / the outer `groupByCrn` of `groupSections`): if multiple CRNs of the same course fully share the lecture meetings and differ only in lab/discussion, the lecture part is shown once and only the differing part is grouped as a "choose an option" list (a UX improvement for large intro courses, e.g. ENGL1102). If there is only one option it is just expanded as a normal section. If all options have the same instructor, instructor info is shown once at the group level too. A section number of "0" isn't real data, so it's hidden in the UI.
- **Deletion is per-course**: "Delete class" in the detail modal removes all `ClassEntry` rows with the same `courseCode` (multiple days) at once — there is no UI to delete only a single day.
- i18n keys are `schedule.*` (`src/i18n/locales/{ko,en}.json`, day labels are `schedule.days.{SUN..SAT}`); Friends-related strings live in a separate `friends.*` namespace.
- **This is the only page that does not use the shared `Page` component**: the calendar grid needs the full width minus the sidebar on desktop, so instead of `<Page>` (max-width 720/960px constraint) it uses its own `S.Root` (an unconstrained flex column). The "add a class" (manual) form and the "search classes" panel used to be inline/drawer, but are now unified to the same `ModalBackdrop` + centered-card pattern as the detail view — follow this pattern when adding a new input form too; do not inline it into the page (there was a problem where input fields stretched abnormally long on wide screens).
- **No fixed top bar, and what that meant for the Friends button**: per CLAUDE.md's "no fixed top bar" rule, the Friends button was originally a global floating corner button too, but after a request that it "only show within the Schedule tab", it now sits inline next to the page title, scrolling with the content instead. Keep this history in mind when adding another cross-tab entry point in the future — design it as a page-local entry point from the start rather than a global floating one.
- **Test coverage**: `layoutDay`/`colorForCourse`/`formatHour` (the grid math) are unit-tested (`src/lib/scheduleGrid.test.ts`); the page's own grid rendering (correct pixel position/height/column-splitting for a given class entry) is component-tested in `src/pages/schedule/SchedulePage.test.tsx`, which mocks `../../lib/amplifyClient`'s `client` directly rather than going through a real request — `ClassEntry` is `allow.owner()`, so it can't be exercised via Playwright's network-boundary mocking (see CLAUDE.md's Testing section for why).
