# SchedulePage

`src/pages/schedule/SchedulePage.tsx` (+ `SchedulePage.style.ts`)

## Purpose

Shows a weekly schedule as a day×time grid, and lets the user add/remove courses in two ways: "search and add" (based on UGA's official schedule-of-classes data) or "add manually" (manual entry). When adding via search, the instructor's RateMyProfessors rating/reviews are shown as well.

## Data sources

- **`ClassEntry` (Amplify model, `amplify/data/resource.ts`)** — the actual stored schedule item. `courseCode` (required), `title`, `day` (required, `SUN`–`SAT` string), `startTime`/`endTime` (required, `"HH:MM"` 24-hour string), `location` (optional, free text). Authorization is `allow.owner()` only — you can only CRUD your own, there is no public read like the community boards. If a course meets on multiple days, one `ClassEntry` row is created per day (managed together by `courseCode` — deletion is also by `courseCode`, removing all day-rows for that course at once, `handleDelete`).
- **`searchUgaClasses` query** (Lambda, `amplify/data/search-uga-classes/handler.ts`) — called by the "Add a class" (search) flow. The "Schedule of Classes" page on `reg.uga.edu` fetches a CSV itself (`apps.reg.uga.edu/soc/{fall,spring,summer}.csv`); the server (Lambda) fetches and parses that CSV instead — the browser cannot fetch it directly because that endpoint has no CORS headers. If `term` is not passed, fall/summer/spring is auto-determined from the current month. It matches by course code / title and returns a meeting list including CRN, instructor, day, time, building, and room — i.e. the search flow auto-fills the room/time.
- **`getProfessorRating` / `getProfessorReviews` queries** (Lambda) — call RateMyProfessors' unofficial internal GraphQL API (`ratemyprofessors.com/graphql`) from the server (not an officially documented API, and RMP also has no CORS, so going through the server is required). Scoped by the UGA school ID (`schoolID`) to match only instructors whose name matches exactly; for same-name instructors it disambiguates with a `department` hint. Ratings are fetched in parallel automatically for every instructor in the search results (`fetchProfessorRatings`), and tapping a rating badge then lazily loads the review detail via `getProfessorReviews`.
- **`fetchUgaBuildings`** (`src/lib/ugaBuildings.ts`) — the list of real UGA building names used for the datalist autocomplete on the "add manually" form's location `<input list>`. Same source as the Map page.

## Things to know

- **The README "Schedule ↔ Map integration" section is partly outdated**: it says "per-class room/time cannot be auto-looked-up, UGA Athena needs SSO", but `searchUgaClasses` (scraping the reg.uga.edu SOC CSV) was added later, so **in the search flow** building/room/time are auto-filled. That said, this is still an unofficial source (a CSV the registration page exposes for its widget), not an official API — it can break silently if the CSV structure changes (column names, etc.). The "add manually" flow is still 100% manual entry, so that constraint still applies there.
- **Location text ↔ map integration**: if you put a UGA building name in `ClassEntry.location` (whether entered manually or auto-filled from search), the Map page matches that name to the real building coordinate and shows a 🎓 marker / highlight. The search result's `building`/`room` are joined into `location` as `[meeting.building, meeting.room].filter(Boolean).join(' ')`, so the search flow now satisfies the "string that starts with a building name" shape the Map-side matching logic expects (with the difference that the room text is appended after, unlike manual entry that puts only the building name).
- **The RMP auth header is a hardcoded fixed value** (`Basic dGVzdDp0ZXN0`) — a public client credential used by RMP's own web app, not a secret, and already a well-known value. There is no separate account/key rotation doc.
- **Same-name instructor matching**: on the RMP side, if there are multiple candidates with an exact name match, it only tries to disambiguate by `department` substring containment — if that fails it just uses the first candidate. There is no guarantee of a perfect match.
- **Course color is hash-based** (`colorForCourse`): the `courseCode` string is hashed base-31 to pick an index into the `category.courses` palette — colors are not stored in the DB, so the same course always gets the same color, but if the palette size changes all existing courses' colors can be reshuffled.
- **Grid layout**: within a day, overlapping classes are split into columns and placed side by side by `layoutDay` (Google Calendar style). The grid's vertical range (`rangeStartHour`/`rangeEndHour`) defaults to 8:00–18:00 but auto-expands if there is an earlier or later class.
- **Section grouping** (`groupSections` / the outer `groupByCrn` of `groupSections`): if multiple CRNs of the same course fully share the lecture meetings and differ only in lab/discussion, the lecture part is shown once and only the differing part is grouped as an "choose an option" list (a UX improvement for large intro courses, e.g. ENGL1102). If there is only one option it is just expanded as a normal section. If all options have the same instructor, instructor info is shown once at the group level too.
- **Deletion is per-course**: "Delete class" in the detail modal removes all `ClassEntry` rows with the same `courseCode` (multiple days) at once — there is no UI to delete only a single day.
- i18n keys are `schedule.*` (`src/i18n/locales/{ko,en}.json`), day labels are `schedule.days.{SUN..SAT}`.
- **This is the only page that does not use the shared `Page` component**: the calendar grid needs the full width minus the sidebar on desktop, so instead of `<Page>` (max-width 720/960px constraint) it uses its own `S.Root` (an unconstrained flex column). The "add a class" (manual) form and the "search classes" panel used to be inline/drawer, but are now unified to the same `ModalBackdrop` + centered-card pattern as the detail view — follow this pattern when adding a new input form too; do not inline it into the page (there was a problem where input fields stretched abnormally long on wide screens).
