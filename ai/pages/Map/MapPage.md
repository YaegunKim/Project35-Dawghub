# MapPage

The most complex screen in the app. A single Leaflet map with 6 layers (each with a visibility toggle + per-category settings modal), GPS/compass location tracking, campus boundary display, and dorm/class markers — all inside `src/pages/map/MapPage.tsx` (~1200 lines). It is supported by 4 popup types (`src/pages/map/popups/*.tsx`), a React→Leaflet mount utility (`reactPopup.tsx`), and a layer-settings localStorage hook (`src/lib/mapLayerPrefs.ts`).

## Purpose

Overlays live buses, library/dining/gym locations + hours, and dorm/academic-building locations on the UGA campus map in one view, and automatically highlights the user's current location, their dorm, and the buildings where they have classes on their schedule.

## Basemap

Vector tiles, not a raster tile provider — `L.maplibreGL({ style: 'https://tiles.openfreemap.org/styles/liberty' })` (`@maplibre/maplibre-gl-leaflet` bridges a MapLibre GL layer into Leaflet's layer system so the rest of the file's markers/polylines/popups stay on the normal Leaflet API). OpenFreeMap is free and keyless with no rate limit. History: OSM's own `basemaps.cartocdn.com` raster tiles → plain `tile.openstreetmap.org` raster (CARTO gated theirs behind an API key) → this vector basemap, once per-layer control (hide dense POI icons while keeping footpaths/roads/building labels — something a pre-rendered raster image can't do) became a real requirement. Requires two `vite.config.ts` entries to actually load tiles in dev — `worker: { format: 'es' }` and `optimizeDeps: { exclude: ['maplibre-gl'] }` — without them maplibre-gl's tile-parsing worker script 404s under Vite's dev-server dependency pre-bundling and the map silently renders only its flat background color with no roads/labels/data (no thrown error, easy to mistake for a totally different bug).

Once our own interactive bus-stop markers (with a live-arrivals popup, see below) existed, the basemap's own bus-stop icon/label became a redundant duplicate — hidden via `basemapLayer.getMaplibreMap().once('load', ...)`, which does two things since the "liberty" style renders a bus stop through two separate layers: `setLayoutProperty('poi_transit', 'visibility', 'none')` (the style's one layer dedicated to bus/rail/airport labels — turned off outright, since this app has no rail/airport stops worth preserving it for) and a `setFilter` on each of the generic rank-tiered POI layers (`poi_r1`/`poi_r7`/`poi_r20` — every other POI class, restaurants/shops/parks/etc., is rendered through these too) adding `["!=", ["get", "class"], "bus"]` to their existing filter, so only the "bus" class point disappears from those shared layers rather than every POI they draw.

## Layer structure

Pressing the circular "Layers" button at top-right (`S.LayersButton`, FontAwesome layer-group icon) opens a **drawer that slides in from the right** (`S.Drawer`, `drawerOpen` state). The 6 rows inside the drawer each correspond to an `L.LayerGroup` (`layersRef.current`), and each row shows a summary of its current settings (e.g. "All routes", "3 selected", "Not set") as a subtitle. Pressing a row opens that category's dedicated **settings modal** — library/dining/gym/academics reuse the shared `LayerChecklistModal` component, while bus and housing have different UI and are written inline. The "Show this layer" switch at the top of each modal replaces the old chip on/off toggle (`toggleLayer(key)`, `map.addLayer`/`removeLayer`). (Even earlier this was an always-on horizontal scrolling legend bar at the top, but since no other tab has a fixed top bar the inconsistency feedback moved it to a top-right button + panel, and this iteration evolved that panel one step further into a drawer + modal — the principle of not having a fixed top-bar UI pattern anywhere in the app still holds.)

- **bus**: a group bundling `routesLayer` (route polylines) + `stopsLayer` (stop markers — a bare `fa-bus` glyph in the route's color, no circle background, sized by `stopMarkerIcon(color, scale)`; `scale` comes from `iconScaleForZoom` recalculated on every `zoom` event so it grows/shrinks continuously like a native map feature would, instead of staying a fixed pixel size like a typical Leaflet marker) + `liveBusLayer` (live bus icons — a white `fa-bus` icon inside a circle colored by route, with heading shown separately as an arrow that swings around the circle's rim — the circle background is what visually distinguishes "a bus is here right now" from a static stop). Polls every 8 seconds (`BUS_POLL_INTERVAL_MS`); position changes move smoothly via a 6-second (`BUS_ANIMATION_MS`) easing animation (`animateMarkerTo`). Pulled out of the layer drawer into a **dedicated bus button at top-left** instead (`S.BusButtonRow`, `useBusLayerPrefs`), alongside two separate pieces of UI: **`S.BusPanel`**, an always-on vertical strip of UGA per-route color+letter badges just below the button row — no need to open anything first; tapping a badge directly toggles `busPrefs.disabledRoutes` for that route, same effect as unchecking it in the settings modal — and **`S.BusSheet`**, opened by pressing the bus button, a bottom sheet (same docked-bottom/scrollable pattern as the Directions sheet below, capped at `42vh` so the map stays mostly visible) for the richer browsing experience, with two views:
  - **Route list** (default): every UGA route **and every Athens Transit route** (see below) merged into one list, sorted by relevance to the user's live GPS location (`currentUserLocation`) — ascending distance from that point to the nearest point on each route's own polyline (`nearestDistanceToRouteMeters`, works identically for both systems since both are just `[number, number][][]` segments), alphabetical as the tiebreak and the fallback before a GPS fix exists. Each row: color+code chip, name, a small system caption ("Bus"/"Athens Transit") plus "Not currently running" when applicable, chevron, and a favorite star. **Nothing is drawn on the map by default** — a route (UGA *or* Athens) only becomes visible once it's favorited or its detail view is opened; `favoriteRoutes` (UGA, `localStorage` `dawghub:map:bus`) and the existing per-route `athensTransitPrefs` (`useFavorites(MAP_ATHENS_TRANSIT_FAVORITES_KEY)`) are both **opt-in** now — Athens Transit used to follow the library/dining/gym "empty checklist = show all" convention, which read as "everything is showing even though I only picked one" once it sat in the same sheet as UGA's opt-in model, so `applyAthensTransitFilter` no longer uses the shared `applyBuildingFilter` helper for that reason. The all-on/all-off eye buttons next to the bus icon and the gear-icon settings modal (UGA only: show/hide-all switch, "show only currently running routes", per-route checklist) are unchanged and layer on top of the favorites check.
  - **Route detail** (tapping a row): back button, color+code badge, name, favorite star, close button, a "N buses active"/"Not currently running" status line, and — **UGA routes only** — a vertical stop timeline (`BusRouteStopTimeline`, own file): a rail through every stop in real travel order, an ETA chip per stop (`computeStopArrivals(stop, [route], buses)`, scoped to just this one route), and each live bus drawn at its **actual interpolated position** between the two stops it's currently between (`locateBusOnRoute` in `passio.ts` — reuses the same nearest-point/forward-distance-along-the-loop math `computeStopArrivals` already has, so there's one implementation of "walk the trace forward, handle the loop wrap" instead of two — returns `{legIndex, progress}`; the component measures each stop row's real screen position via `useLayoutEffect` + refs and lerps between the two rows' centers, applied by mutating `.style.top` directly on a ref rather than a React-state-driven inline `style={{}}` prop, since CLAUDE.md forbids that in JSX and the offset only exists after layout anyway). **Athens routes get no stop-list section**: `AthensStop`/`AthensRoute` have no per-route ordered stop list at all (GTFS `stop_times`/`trips` were never extracted by `scripts/fetch-athens-transit-data.mjs`), so there's no real sequence to build a timeline from — see the Athens bullet below for how its stop *dots* are approximated instead. Opening either kind of detail view always previews that one route on the map regardless of favorites/settings (`setBusSheetFocus` for UGA / `setAthensSheetFocus` for Athens, both mirroring `directionsBusFocus`) and fits the map to its full loop (`focusRouteBounds` / the bounds-fit inside `focusAthensRoute`).
  - **Tapping a stop row** (UGA route detail only) flies the map to that stop and opens its existing `MapStopPopup` (see below) showing *every* route serving it, not just the one currently selected — `stopMarkers` gained an `id` field for this lookup, and a `stopFocus: string[] | null` override (the serving routes' names) sits in `routeVisible`/`stopVisible`'s precedence chain between `busSheetFocus` and the normal favorites check, so all of those routes render together while a stop is focused (`focusedStopId`/`setFocusedStopId` React-side, cleared on going back to the list or closing the sheet).
  - **A stop is shown if any route that actually serves it is currently visible** — `stopMarkers` carries a `routeNames: string[]` per stop, computed the same way `computeStopArrivals` does (via `PassioRoute.stops` membership matching by stop `id`, not the unreliable `PassioStop.routeName` tag a physical stop only carries one of, even though several routes commonly run through it — confirmed: none of Central East's 19 real stops are tagged routeName "Central East"). `stopVisible` in `refreshBusVisibility` then just OR's `prefsShowRoute` (the same hideAll/favorites/per-route-disable/operating-only check routes themselves use) across that stop's `routeNames`, so a stop only appears once at least one route touching it is visible. For future arrival-time stats, `amplify/data/log-bus-arrivals` polls Passio directly from the server every minute and keeps appending (bus, stop) proximity samples to the `BusStopArrival` table (still early-stage — not enough history yet to actually compute stats from). **Tapping a stop opens `MapStopPopup`** (`src/pages/map/popups/MapStopPopup.tsx`), listing every route that actually serves it — via `computeStopArrivals` in `passio.ts`, which checks `PassioRoute.stops` membership (not the unreliable `routeName` tag) — each with a live ETA for its nearest bus. That ETA walks the *route's real GPS trace* from the bus's nearest point to the stop's known `polylineIndex` (looping past the end back to index 0 for a bus that's already passed the stop this lap), not a straight line, for the same reason `PassioRoute.stops` itself exists: a bus that looks close as the crow flies can be on the far side of the loop. The popup re-invokes its `getArrivals` getter every 5s (`REFRESH_INTERVAL_MS`) so it keeps tracking real bus movement while left open, reading a `latestBuses` closure variable that `pollBuses` updates every tick — no separate fetch of its own.

## Directions

Pressing the second button just below the top-right Layers button (`S.DirectionsButton`, `faRoute` icon) enters Directions mode — the Layers/Directions/Bus corner buttons all hide at that point (so they don't fight the Directions UI for the same top-of-screen space; opening Directions also force-closes an open bus sheet via `closeBusSheet` and vice versa, only one sheet is ever open at once), and a single docked-bottom sheet appears instead (`S.DirectionsBottomSheet`, same shape as the bus sheet, capped at `45vh`): the origin/destination fields + "Get directions" button show as soon as the sheet opens, and once a search runs, the walk-only/walk+bus results list (or, once navigating, the turn-by-turn nav HUD) appears beneath them in the same scrollable sheet. The map itself stays visible and interactive above it. This used to be a top-docked bar (fields) + a separate bottom sheet (results) — merged into one bottom sheet so Directions docks the same edge as every other panel in this app (bus sheet, layer drawer) instead of being the one exception pinned to the top. Unlike CLAUDE.md's app-wide "no fixed top bar" rule, this is a temporary overlay that only appears while Directions is active, so it gets the same exception as the layer drawer.
- **The sheet is compressed to take up as little space as possible while just showing the form**: no separate title row — the origin/destination input rows (each marked with a circle/square dot instead of a FROM/TO label — `S.DirectionsFieldDot` — with placeholder text doing the labeling instead, to save row height) sit next to a `S.DirectionsActionsColumn` that stacks the swap/close buttons vertically, fitting inside the fields' own height with no separate header row. The "Get directions" button is also its own slim 32px `S.DirectionsSearchButton` instead of the shared 40px `Button`.
- **Origin/destination fields use a custom autocomplete** (`BuildingAutocomplete`, own file), not a native `<input list="...">`/`<datalist>` — Chrome's native datalist popup ignores CSS entirely (its width/position are browser-controlled), which read as visibly broken once the field itself lived in a width-constrained bottom sheet. It's a small self-contained combobox: while focused and non-empty, an absolutely-positioned `<ul>` of matching `allBuildingNames` (case-insensitive substring, capped at 8) sized to exactly the input's own width. Suggestion rows use `onMouseDown` + `preventDefault()` (not `onClick`) so a click registers *before* the input's own `onBlur` (delayed 100ms for exactly this reason) would otherwise close the list first.

- **Trip planning**: `planTrip(origin, destination, routes)` in `src/lib/directions.ts`. The walk-only option is always computed. For walk+bus, every route gets up to **4 candidate stops per side** within a 1200m radius of the origin and destination, and every combination of those is evaluated (picking just the single nearest stop on each side can land a combo that rides a route almost all the way around in the wrong direction before reaching the actual destination side — a real bug this ran into) → only the top routes by best combo get a real walking-API lookup for final candidates. The walking legs come from OpenRouteService (`amplify/data/get-walking-route`) as real sidewalk routes; the bus leg is drawn (not as a straight line) by slicing the route's real GPS trace using `PassioRoute.stops`' `polylineIndex` (the stop order, built in `src/lib/passio.ts` from Passio's actual per-route stop sequence — `PassioStop.routeName` only names one owning route per stop and can't be trusted on its own). Duration is estimated as `distance ÷ an assumed average speed + a fixed wait time (5 min)`, since Passio has no arrival-prediction API, and the UI marks it as an estimate (`busEtaApprox`) — to allow for that estimation error, a walk+bus combo up to 3 minutes slower than walking is still shown as "worth comparing" rather than requiring it to always be strictly faster. Once `BusStopArrival` has enough data, only this one estimate function needs to be swapped out.
- **The ORS API key is managed via Amplify `secret()`** — the first secret used in this project. `secret('ORS_API_KEY')` in `amplify/data/get-walking-route/resource.ts`; the value has to be set by hand with `npx ampx sandbox secret set ORS_API_KEY --profile dawghub` (can't be automated from code). Without it, the `getWalkingRoute` query fails with 401 and the UI just shows the `errorGeneric` message.
- **Popup "Directions" button**: present on every popup except bus stop/route popups (library/dining/gym/dorm/academics, via the shared `MapDirectionsButton` component). Pressing it calls `mapActionsRef.current.startDirectionsTo(point)`, which fills that point in as the destination, the current GPS location as the origin, opens the panel, and immediately triggers the trip search via the `autoSearchPending` flag (matches Google Maps' "tap a place → Directions" flow).
- **Picking a point by tapping the map**: a map click only drops a pin while `pickingFor` is `origin`/`destination` — Leaflet's `Path` layers (`L.circleMarker`, used by housing dots and Athens Transit stops) default `bubblingMouseEvents` to `true`, so those two spots explicitly set it to `false` so their popup still opens during pick mode without also dropping a stray pin. `L.Marker`-based layers (library/dining/gym, `HOUSE_ICON`, bus stops, academics' `MY_ACADEMIC_ICON`) don't need this — `Marker.options.bubblingMouseEvents` already defaults to `false`. The hint text (`pickHint` + cancel) is a top-anchored, viewport-relative toast (`S.PickToast` — the same component Schedule's "set location" flow uses for its own pick-mode hint) rather than something nested inside the sheet: the sheet is bottom-docked with `overflow-y: auto`, so an absolutely-positioned child trying to float just outside its bounds would get clipped by the sheet's own scroll container.
- **Drawn on its own layer** (`directionsLayer`, not part of the layer drawer) — only the origin (A, green) / destination (B, red) pins and the currently selected option's route are drawn (never both options at once; switching options redraws). Closing the panel resets the search state, pins, and route entirely.
- **`fitBounds` uses asymmetric padding sized to the bottom sheet**: every time a route is drawn, it reads `bottomSheetRef` (`useRef`, attached to `S.DirectionsBottomSheet`)'s `getBoundingClientRect().height` and feeds that into `paddingBottomRight` (top padding is just a small fixed constant now that nothing docks to the top). The ref is held by the map setup effect's closure (which runs once on mount), but since the ref object itself stays the same across renders, `.current` always points at the latest DOM height. The bus sheet's own `focusRouteBounds`/`focusAthensRoute` do the analogous thing with a separate `busSheetRef`.
- **Turn-by-turn navigation auto-follows GPS, but a manual drag pauses that** (`isFollowingUser` state): once "Go" starts navigation (`navigating`), the map keeps `panTo`-ing to the user's live position on every GPS update. Originally this had no way to look around — dragging the map to check something ahead would just get yanked back to the GPS dot on the very next position update. A `dragstart` listener (registered once at map-mount, harmless when not navigating since nothing reads the flag then) sets `isFollowingUser` to `false`, which the auto-pan effect checks before calling `panTo` — a "re-center" button (reusing the Layers button's top-right slot, since Layers/Directions are always hidden while navigating) appears only in that state and sets it back to `true` plus immediately re-centers on tap. `isFollowingUser` resets to `true` automatically every time a fresh navigation starts.
- **While a trip is showing, the bus layer only shows what's relevant to that trip** (`setDirectionsBusFocus`, `refreshBusVisibility`): when viewing a walk+bus option, only the ridden route's line (solid, heavier weight), stops, and live buses render normally, and **every other route's stops/live buses are hidden outright** (not just dimmed — so there's no room to misread a stop as "could I also catch a bus here?"), leaving only that other route's line visible as a thin dashed reference. When viewing the walk-only option, or when there's no bus option at all, routes/stops/live buses are hidden **entirely** (there's no reason for a bus to be visible on a walking-only trip). With no trip showing (panel closed, or before a search), this override turns off and the usual layer settings (`busPrefs`'s favoriteRoutes/hideAll/disabledRoutes/operatingOnly) apply again — unless the bus sheet has its own override active, which takes over next in the same precedence chain (`routeVisible`/`stopVisible` in the map effect: `directionsBusFocus` → `busSheetFocus` → `stopFocus` → the normal favorites-based prefs).
- **library**: the 9 buildings defined in `LIBRARY_BUILDING_NAMES`, book-open-reader FontAwesome icon. Popup is `MapInfoPopup` + today's hours (LibCal). The modal picks which buildings to show via a per-building checklist (`useFavorites('dawghub:map:library')`, all-unchecked = "show all").
- **dining**: the 6 in `DINING_BUILDING_NAMES`, utensils icon. Popup is `MapDiningPopup` (today's hours + a live query of the current meal's menu via the `getDiningMenu` Lambda + a `/dining/:hall` link). Checklist follows the same pattern as library (`dawghub:map:dining`).
- **gym**: the 2 in `GYM_BUILDING_NAMES` (Ramsey Center, Pound Hall), dumbbell icon. Pound Hall's popup label is hardcoded to "Pound Hall & Wheeler Gym" (two buildings sharing one facility). Checklist follows the same pattern (`dawghub:map:gym`).
- **housing**: every building with `buildingUse === 'Housing'` shown as a radius-2px `circleMarker` (dot). Click opens `MapDormPopup` — a "Set as my dorm" toggle (the existing mechanism is unchanged). In the modal, instead of a checklist there is a search input (datalist autocomplete) + a save button to set the same `myDormBuilding` — the designated dorm is shown as a house-shaped (`faHouse`) marker instead of a dot (`HOUSE_ICON`, `refreshDormHighlight`).
- **academics**: it no longer shows all 318 academic buildings; markers are created **only for buildings matched against my schedule (`ClassEntry.location`)** (`entriesByBuilding`). The modal's checklist picks which of those to actually show on the map (default is show all) — the result is saved to `MapPreference.myAcademicBuildings` (Amplify). Click opens `MapAcademicPopup` — the list of my classes that meet in that building (read-only).
- **athensTransit**: Athens-Clarke County's own city bus system (`src/lib/athensTransit.ts`) — a completely separate agency from UGA's Passio-based campus buses above, running on the Avail/AvailTec InfoPoint platform and speaking industry-standard GTFS/GTFS-Realtime (binary protobuf, decoded with `gtfs-realtime-bindings`) instead of Passio's plain JSON. **Merged into the bus sheet's route list** (see above), but **only the routes that actually reach campus** — `campusRelevantAthensRouteIds(routes, stops)` (pure function, unit-tested in `athensTransit.test.ts`) keeps a route only if at least one of its real stops (see `stopIds` below) is either (a) actually inside UGA's Athens campus boundary — `isPointOnUgaAthensCampus`, real point-in-polygon membership against the surveyed OpenStreetMap boundary in `campusBoundary.ts`, not an approximated radius — or (b) a student apartment/townhome complex within `ATHENS_CAMPUS_APARTMENT_PROXIMITY_METERS` (700m) of that boundary, detected by matching `stop.name` against `ATHENS_APARTMENT_STOP_NAME_PATTERN` (GTFS stop names already spell these out, e.g. "Riverbend Pkwy at Players Club Apts OB" — a real signal in the data, not a hardcoded complex list). A qualifying route is kept **whole** — every stop it serves city-wide, not just the campus-adjacent ones — since the filter only decides inclusion, never trims. Of the 18 real ACC Transit routes this currently keeps 7 (as of the last `pnpm data:athens-transit` refresh); re-run that script and re-check if ACC changes its route network. Kept routes sort into the same GPS-relevance list as UGA routes (see above), with their own favorite star. Route **metadata** (names/colors/shapes/`stopIds`, not live positions) loads via a separate `useQuery(['athensRoutesAndStops'], fetchAthensRoutesAndStops)` gated on `enabled: busPrefs.panelOpen` — decoupled on purpose from the heavier imperative Leaflet setup below (`loadAthensTransit`, which builds the actual polyline/marker objects and starts live polling): the *list* needs names the moment the sheet opens, before any route has been favorited or tapped, or there'd be nothing to tap to trigger that heavier setup in the first place. Cheap either way — `fetchAthensRoutesAndStops` is a local dynamic `import()` of a committed JSON snapshot, not a network call. Selecting an Athens route from the sheet reuses the drawer's own activation path (`toggleLayer('athensTransit')`, not a bare `setVisible` call — that would flip the state flag without actually attaching `athensTransitGroup` to the map) and drives an Athens-side mirror of the UGA bus-sheet-focus mechanism: `athensSheetFocus`/`setAthensSheetFocus` overrides `applyAthensTransitFilter` down to just that one route (by its `athensRouteLabel` — `` `${shortName} · ${longName}` ``) and filters `athensLiveBusLayer` to just its own buses (`athensBusRouteLabelById`), then `focusAthensRoute` fits the map to that route's real segments. **Opt-in, not "empty checklist = show all"**: `applyAthensTransitFilter` doesn't use the shared `applyBuildingFilter` helper (same "unchecked = show everything" convention as library/dining/gym), which read as broken once Athens routes sat in the same opt-in-by-default sheet as UGA's — selecting one route left every *other* Athens route's line/live-buses still showing via that fallback. It filters `athensRouteMarkers`/`athensLiveBusLayer` directly against the effective selection (`athensSheetFocus` if set, else `athensTransitPrefs.favorites`) with no "empty = all" case. The layer drawer's own Athens Transit row (`LayerChecklistModal`, same as library/dining/gym/academics) still exists as a secondary settings surface and is unaffected by the campus-relevance filter above (it lists all 18 routes, opt-in there too — subtitle reads `t('map.showNone')` instead of `t('map.showAll')` when empty). **Stops now get real per-route filtering**: `AthensRoute.stopIds` (a `string[]` of real GTFS `stop_id`s, unioned across every trip on that route) is extracted from GTFS `stop_times.txt`/`trips.txt` by `scripts/fetch-athens-transit-data.mjs` — a file the script was already downloading but not parsing — so `refreshAthensStopVisibility` does a true membership check (`visibleRoutes.flatMap(route => route.stopIds)`) instead of the straight-line-proximity-to-the-route's-own-polyline approximation it used before (which could both miss real stops and wrongly include ones a route doesn't actually serve, especially where routes bundle tightly downtown). With no route focused or favorited, Athens stops are still hidden **entirely** rather than falling back to "show all 509 of them" — that's still noise, not information, even with real per-route data (Athens routes still get no `BusRouteStopTimeline` in their detail view either — GTFS `stop_times` gives membership, not a single canonical ordered sequence per route, since most routes run two directions). Route/stop shape data (a ~190KB JSON snapshot, `src/lib/athensTransitData.json`, refreshed by hand via `pnpm data:athens-transit` → `scripts/fetch-athens-transit-data.mjs`, which also Douglas-Peucker-simplifies each route's shape to ~8m tolerance — the raw GTFS shapes.txt is ~6x denser than needed at any zoom this app shows) isn't fully built into Leaflet markers until `loadAthensTransit` actually runs (guarded by an `athensLoaded` closure flag so it only ever runs once), triggered either by the drawer switch or by selecting an Athens route in the bus sheet. Live bus polling (`pollAthensBuses`, same 8s/`BUS_POLL_INTERVAL_MS` cadence and `busHeadingIcon`/`animateMarkerTo` reuse as the UGA bus layer) similarly only runs while the layer is active — `setAthensTransitActive` starts/stops the interval, since a hidden layer's bus positions going stale doesn't matter and there's no reason to hit a third-party government server on every student's phone for a feature most won't turn on.

Common: icon-style markers registered in `zoomAwareMarkers` (library/dining/gym/academics) switch to the full icon when zoomed in (`BASE_ZOOM=15` or above) and to `dotIcon` when zoomed out (`updateMarkerDetail`, `zoomend` event). Academic markers register themselves into `zoomAwareMarkers` inside `applyAcademicMarkers` (not at buildings-query time like library/dining/gym, since they're redrawn from scratch on every schedule change) — that function also has to prune its own markers back out of `zoomAwareMarkers` before rebuilding, or stale entries from a previous redraw pile up. Library/dining/gym/academics/bus-route markers are not added to their layer immediately on creation; they are held in a `{name, marker}` tracking array and the `applyXFilter(selected)` function decides actual visibility based on `layer.hasLayer(marker)` (re-invoked on every checklist change).

### Why storage is split (account vs localStorage)

Bus mode / selected routes and the selected library/dining/gym buildings are pure display settings that can change often, so they are saved to `localStorage` (`dawghub:map:bus/library/dining/gym`) — sending a GraphQL mutation every time would only add RPC load, and cross-device sync is not essential. Conversely, "my dorm" and "my academic buildings" are low-frequency settings closer to "who I am", so they stay in the existing `MapPreference` Amplify model (`myDormBuilding`, `myAcademicBuildings`) — the fields were already in the schema (no migration needed).

## Data sources

- **Live bus position / routes / stops**: Passio GO (`src/lib/passio.ts`, `fetchUgaBuses` / `fetchUgaRoutesAndStops`) — UGA system id `3994`, CORS is open so the frontend polls directly.
- **Building coordinates + use (BuildingUse)**: a static JSON snapshot (`src/lib/ugaBuildingsData.json`) taken from UGA ArcGIS (OUA) via `pnpm data:buildings` (`scripts/fetch-uga-buildings.mjs`) and committed to the repo — `fetchUgaBuildings()` (`src/lib/ugaBuildings.ts`) is no longer a live call, it just returns this JSON. The library/dining/gym/housing/academics layers are all filtered from this. `MANUAL_BUILDINGS` adds 3 new buildings not in the GIS (Hillside Dining Commons, The Niche, Village Summit Dining Commons) with estimated coordinates. Re-run the script and commit whenever a new building goes up on campus.
- **Library hours today**: LibCal (`src/lib/libraryHours.ts`, used in the library popup).
- **Gym hours today**: `src/lib/gymHours.ts`, hardcoded by manually parsing the Rec Sports PDF (needs a manual update each semester — see README "External data sources" for details).
- **Dining menu**: the `getDiningMenu` Lambda query that proxies Nutrislice (queried live each time a dining popup opens).
- **Campus boundary polygons**: `src/lib/campusBoundary.ts` exports `UGA_CAMPUS_BOUNDARIES`, one dashed polygon per UGA campus statewide (Athens Main, Athens Health Sciences, Griffin, Tifton, Gwinnett, Skidaway Institute of Oceanography, Marine Institute/Sapelo Island) — not just Athens. Athens Main is a static coordinate array taken from OpenStreetMap relation 21071510 (ODbL); Griffin/Tifton/Athens Health Sciences/Gwinnett are individual OSM ways (Gwinnett's way is tagged with a stale business name in OSM but its address matches UGA's published campus address). Skidaway and Sapelo have no single boundary polygon in OSM, so those two rings are convex hulls computed over their building footprints instead of a surveyed boundary — expect them to be a looser, less precise outline than the others. Unlike most decorative layers on this map, these are `interactive: true` with `bindTooltip` so hovering shows which campus it is, since most of them have no other context nearby to identify them (they're hundreds of miles from Athens and none of the app's other layers — buildings, dining, buses — have data there).
- **My dorm**: the `myDormBuilding` field of the `MapPreference` model (`src/lib/mapPreferences.ts`, a singleton "create if missing" caching wrapper).
- **Football schedule/live score (Sanford Stadium marker)**: the `getFootballSchedule` custom query (`amplify/data/get-football-schedule/handler.ts`) probes `data.ncaa.com/casablanca/scoreboard/football/fbs/{year}/{week}/scoreboard.json` across ~20 week numbers in parallel and filters down to Georgia's games — NCAA's own public scoreboard JSON (the same data ncaa.com's site loads client-side; no API key, but also not a documented/stable API). This runs **server-side in a Lambda, not directly from the browser**, because that endpoint sends no CORS headers (unlike Passio's bus API) — `src/lib/footballSchedule.ts`'s `fetchGeorgiaFootballSchedule(year)` just calls `client.queries.getFootballSchedule({ year })`, same pattern as `fetchWalkingRoute`/`getWalkingRoute`. A single fixed marker at Sanford Stadium (verified via Nominatim, not part of the layer drawer — same "always on" treatment as the campus boundary polygon) shows white normally and flips to brand red with a "Game Day!" tag (`isFootballGameDay` — true if any game is live or scheduled today) via `applyFootballMarker`/`mapActionsRef`, following the same "useQuery at the top + imperative redraw via mapActionsRef" pattern as the academic markers. Its popup (`MapFootballPopup`) shows the next/live game via `pickRelevantGame`. `staleTime` is long (1h) since the schedule itself barely changes, but `refetchInterval` switches to a 15s poll only while the cached data contains a `gameState: 'live'` game, so the score/clock stay fresh during an actual game without polling the rest of the time.
- **Buildings where I have classes**: subscribes reactively to the `ClassEntry` model (`amplify/data/resource.ts`) via `useQuery(CLASS_ENTRIES_KEY)` (reusing the exact same cache the Schedule page writes to under that key) → calls `mapActionsRef.current.applyAcademicMarkers` to fully redraw the markers whenever that result changes. Matches each `location` string against ArcGIS building names via `findBuildingByName` to build a per-building class list (`entriesByBuilding`) — adding/removing a class on Schedule makes the markers follow automatically, either the next time the map is opened or the moment the cache refreshes while it's already open.

## Things to know

- **Location tracking starts automatically when the map mounts; only the compass permission still needs a user gesture**: `startTracking` is called once as soon as the map appears, as if the bottom-left 📍 button (`LocateControl`) had been auto-clicked (you can still tap it to turn tracking off and back on, `stopTracking`). But `DeviceOrientationEvent.requestPermission()` must be called inside a user-gesture handler on iOS Safari for the permission prompt to appear, so the auto-start path can't obtain the compass heading-cone permission — on iOS the user has to actually tap the button once before the cone shows up. If permission is denied/unsupported/never requested, only the GPS coordinate is shown, with no compass heading cone.
- **The compass heading source differs per platform**: iOS uses `webkitCompassHeading` (non-standard, preferred); other browsers use the `alpha` value from `deviceorientationabsolute`/`deviceorientation`, converted as `(360 - alpha) % 360`. Both listeners are registered and whichever produces a value is used.
- **Setting a dorm = clicking a map dot or the layer modal, both the same field**: clicking a dorm dot on the map and toggling in `MapDormPopup`, or setting it via the search input in the layer drawer → housing modal — both save the same value to Amplify via `updateMapPreference({ myDormBuilding })` (unified through `mapActionsRef.current.setMyDorm`). The set building turns from a dot into a house-shaped marker (`HOUSE_ICON`) (`refreshDormHighlight`). Only one can be set at a time (designating a new dorm auto-clears the previous one).
- **Academic buildings get markers only for "buildings where I have classes", and a checklist picks which of those to show**: marker creation itself is automatic (only buildings present in `entriesByBuilding`, the result of matching `ClassEntry.location`); whether to actually display each on screen is chosen via the checklist in the layer drawer → academics modal (default shows all candidates, saved to `MapPreference.myAcademicBuildings`). Since every building that has a marker means "a building where I have classes", they are always highlighted purple (`MY_ACADEMIC_COLOR`) — there is no separate grey/purple distinction. Styled the same icon-on-disc way as library/dining/gym (`MY_ACADEMIC_ICON`, graduation-cap glyph) rather than a flat colored circle, and — like those three — shrinks to `MY_ACADEMIC_DOT` when zoomed out.
- **Dot markers are very small at radius 2px (`BUILDING_DOT_RADIUS`)**: barely visible until you zoom in, just enough to register a click — this is intended (code comment: "barely visible until you zoom in, just enough to click"). This applies to the plain housing dots specifically — unlike the icon-style layers (library/dining/gym/academics), that radius does not grow with zoom, it's always the same.
- **Popups render real React components**: `bindReactPopup` (`reactPopup.tsx`) mounts them onto a detached DOM node with `createRoot().render()` and passes that to `marker.bindPopup()`. For cases where popup content changes asynchronously after it opens (like the dining popup), a `ResizeObserver` detects content-size changes and calls `popup.update()` — without this observer the popup shows clipped content after the menu loads.
- **Bus markers are reused by ID**: markers are not recreated every poll; they are cached by id in the `busMarkers` Map, and only buses that disappeared are removed from the layer — that is why positions animate continuously with no flicker.
- **Map/subscription teardown is all handled in `useEffect` cleanup**: `watchId` clear, removal of both kinds of orientation listener, `setInterval` clear, and `map.remove()` — so leaving and re-entering the page never leaves duplicate polling/listeners behind.
- **The zoom-level display control** shows not the actual Leaflet zoom value but the icon scale (%) computed by `iconScaleForZoom()` — when debugging, do not mistake the number at bottom-right of the map for the "zoom level".
- **Test coverage**: the dining-hall `mapIntent` handoff (focus zoom+ripple, and directions with GPS-delayed origin autofill) is covered end-to-end in `e2e/dining-map-handoff.spec.ts`, using a full `navigator.geolocation` replacement (`e2e/fixtures/geolocation.ts`) to fire GPS fixes on demand instead of relying on Chromium's built-in (and here, unusable) geolocation mock.
